# 体素场景使用手册（真人操作版）

这份手册面向自己动手验证的人：从启动工作台、上传参考图生成一个体素场景，到看懂页面上的每个阶段和结论。安装依赖请先按 [从零运行手册](run-from-zero.md) 完成；体素模式的技术细节见 [体素场景运行说明](voxel-scenes.md)。

## 1. 能得到什么、不能得到什么

- **能得到**：一个可运行、可编辑的语义体素场景。场景由带名字的实体（墙、柱、水池、植被……）组成，导出 `.vox`（MagicaVoxel 可打开）和 Engine 运行包，并附上原图、Engine 截图、录屏和独立评分证据。
- **不能保证**：与参考图像素级一致。一张图看不到背面，模型也可能误判比例与遮挡。页面上的“通过/未通过”只针对本次输入的本次结果，不是稳定成品率认证。

## 2. 启动

在仓库的 `workbench/` 目录启动后端（默认使用本机已登录的普通 `codex` CLI）：

```sh
cd workbench
PORT=19774 PIPELINE_PROVIDER=codex-cli PIPELINE_CODEX_BIN=codex \
  PIPELINE_QUALITY_VERSION=scene-quality-v7 PIPELINE_DELIVERY_STANDARD=basic70 \
  bun src/server.ts
```

- 看到 `SCENE_WORKBENCH http://127.0.0.1:19774/` 即启动成功。端口被占用时换一个，并在下文对应替换。
- `PIPELINE_MAX_CALLS` 控制累计模型调用上限（含重试、格式纠正和评审）。一个体素场景实测约 40–50 次调用，若设上限请留够余量；预算耗尽的任务不会自动续跑。
- 想换模型或思考深度，在页面上选择即可；也可用 `PIPELINE_MODEL`、`PIPELINE_CODEX_EFFORT` 设置推荐值。
- 不要把 `.env`、`workbench/data/`、生成物或私有依赖提交到 Git。

自检（另开终端）：

```sh
curl -fsS http://127.0.0.1:19774/api/state | python3 -c 'import json,sys; d=json.load(sys.stdin); print(d["budget"]["configured"], d["budget"]["model"])'
```

`configured` 为 `True` 才开始生成。

## 3. 生成一个体素场景

1. 浏览器打开 `http://127.0.0.1:19774/voxel/`（或首页侧栏“体素场景”），点击“＋ 新建体素场景”。
2. 上传同一场景的 1–5 张体素风格图片，可在“补充说明（可选）”里写想保留的要点。
3. 选择“本地 Codex 模型”和“思考深度”。复杂场景建议用较强模型、较高深度。
4. 选择“生成方式”：
   - **按验收目标生成**：持续修正，直到达标或连续无有效改善才停止（推荐）。
   - **生成并有限修正**：只做有限几轮修正。
   - **仅首轮生成与验收**：只生成一次并评分，最省调用。
5. 点击“开始生成体素场景 →”。图片会被自动冻结为本次生成与验收的共同目标，不需要再人工确认。

一个较复杂的场景（例如神庙）实测要数十分钟到数小时。关闭页面不会中断生成，回到“▦ 体素生成记录”即可继续查看。

## 4. 看懂生成过程

任务详情页的“生成进度”按阶段推进，“查看执行过程和实时模型输出 ↗”可以看到每一步的模型输出。主要阶段如下。

### 4.1 观察与规划

模型逐图观察，列出关键物体、组件、开口和它们的空间关系，再规划布局与参考机位。规划阶段会做两项机械检查，不合格会当场退回重做：

- **主体占幅**：被标为 subject 的主体，在参考机位里的高度不能低于画面的 25%。
- **实体总数**：全场景实体不超过 64 个。

### 4.2 空间灰模（最关键的一关）

先用纯几何的灰模在真实 Engine 里渲染，确认布局对了再做细节。体素灰模采用**客观验收**（`voxel-objective-acceptance-v1`），全部满足才算通过：

| 检查 | 含义 |
| --- | --- |
| 证据完整 | 截图、渲染回执、测量齐全 |
| 关键物体存在 | 观察阶段列出的关键物体都有实例 |
| 关键关系不低于 2.5 | 评审对每条**布局级**关键空间关系的打分，最低一条 ≥ 2.5 |
| 关键物体可见 | 参考机位里实际看得到（有像素） |
| 没有左右镜像 | 布局方向与原图一致 |
| 地标对齐 | 地标位置误差 ≤ 0.10（画幅比例） |
| 完整范围 | 场景外轮廓误差 ≤ 0.15 |

观察阶段会把每条关系标成 **layout（布局级）** 或 **detail（细节级）**：
- 布局级：建筑/主体/大构件之间的左右前后、尺度比例、遮挡、通道、纵深和整体轮廓，灰模必须做对；
- 细节级：立面上的窗洞与开口排布、招牌/外机/管线/灯具等附着小件的分布、店面与装饰，灰模里是统一灰色，很难看清，这类关系不阻断灰模，评分记在 `gate.json` 的 `objective.deferredDetail`，并作为必须实现的目标交给对应资产。

页面上 VLM 评审的空间总分（如 3.1）**只作参考**；`passed` 以上表的客观结论为准，评审结论另记为 `vlmPassed`。

未通过时，程序把**具体阻断项**（哪条关系太低、哪个地标被挡住看不见）交给修正模型，最多进行有限轮修正：

- 某轮阻断项比当前最好的一轮少，就保留这一轮作为新基准；否则这一轮被拒绝，记一次“无改善”。
- 连续 2 轮无改善即停止，状态为“按质量边界停止”。
- 接近门槛时会追加 2 次独立评审，取多数意见，减少评审本身的随机性。

### 4.3 资产与细节

灰模通过后，按实体逐个生成详细资产，每个资产都要在 Engine 里实际预览通过。资产必须沿用灰模冻结的格距、范围和姿态，只能换材质、加细节。需要保留表面颜色的实例，会明确告诉模型哪些材质来源必须用上。失败的资产保留上一个有效检查点，不会拖垮整个场景。

### 4.4 体素化、运行与成品评分

程序把几何转成体素格（`voxel-grid-v2`），重新构建 Engine 场景、采集截图录屏，再由独立评审按 **basic70** 标准打分：

- **原始诊断分（rawScore）≥ 70**；
- 而且没有已确认的强制规范缺陷，常见的是 **S06**（轮廓可读性）和 **S13**（没有明显的结构缺陷，如墙体缺口、悬空水面）。

两条都满足才是“交付通过”。页面上常见两个分数：例如 `87.5` 是加权总分，`77.76` 是原始诊断分，basic70 看后者。

未达标时会进入“视觉修正”循环：每轮先选出最影响整体的修正目标，再修改、重新体素化、运行和评分。最终保留最好的一轮。如果修正模型确认在冻结约束内没有合法改法（例如只能削切冻结的灰模种子），循环会就此结束，执行过程里显示“没有合法改法，保留此前最佳候选”，任务以最好一轮的状态（通常是 `needs_review`）结束，而不是报错。

## 5. 看结果

- **生成结果与验收**：最终状态、分数、未通过原因（例如“已确认的规范缺陷：S13”）。
- **验收依据与差距**：每个维度的评分理由和对应截图。
- **打开三维场景**：在浏览器里交互查看 Engine 场景。
- **下载可编辑 .vox**：可用 MagicaVoxel 打开、编辑。
- **下载运行场景和证据**：运行包与全部回执。
- **体素物料 / 查看全部实体资产 ↗**：逐个实体的资产与预览。

状态的含义：

| 状态 | 含义 |
| --- | --- |
| `passed` | 本次输入达到交付标准 |
| `needs_review` | 场景可运行，但质量未达标或有待复核项 |
| `failed` | 某一阶段报错终止；**已产出的最好一轮仍保留**，可以打开、下载 |
| `blocked` | 外部条件阻塞（预算、网络、认证），见下节 |

## 6. 中断与继续

- **网络中断**：恢复次数耗尽且确实是连接失败时，详情页会出现“网络恢复后继续 / 确认网络已恢复并继续”，只提供一次。
- **按诊断修正空间 / 按已更新的规划继续 / 继续已保存空间候选**：只在程序已有经过验证的新机制、且满足条件时出现，会保留原需求、原调用记录和预算。
- **模型连接卡住**：带工具的调用连续 10 分钟没有任何输出时，会提前停止并按临时连接故障自动重试（仍受每步最多 3 次、总时长 1 小时的限制），不会再干等到时限。
- 预算耗尽、用户取消、认证失败不能靠这些入口绕过。想重试就新建任务，不要删除失败记录。

## 7. 运行数据在哪里

每个任务的全部数据都在 `workbench/data/runs/<任务ID>/`（若设置了 `PIPELINE_DATA_DIR`，则在该目录的 `runs/` 下）：

| 位置 | 内容 |
| --- | --- |
| `job.json` | 任务状态、各阶段、最终错误 |
| `generation/blockout/<轮次>/gate.json` | 灰模每轮客观验收：`passed`、`vlmPassed`、各项检查与阻断项 |
| `iterations/<轮次>/` | 每个视觉修正轮次的场景、体素、截图和评分（`delivery-assessment.json`） |
| `voxel-source-scene.json` | 冻结的制作源（体素化之前） |
| `scene.vox` / `voxel-program.json` | 可编辑体素 / 可回放占用格 |
| `delivery-assessment.json` | 最终 basic70 结论与原因 |
| `data/model-budget-*.json` | 累计模型调用数 |

## 8. 当前效果与已知限制（2026-10-19）

在复杂的神庙参考图上做了三次完整的网页端到端验证（codex 系列模型，xhigh 深度）：

| 阶段 | 结果 |
| --- | --- |
| 空间灰模 | 三次都通过客观验收（第 0、2、3 轮）。此前同一场景从未通过 |
| 资产 | 全部首次通过 |
| 成品原始分 | 64.6 → 72.6、74.9 → 77.8；最新一次第 0 轮即 78.2 |
| 最终交付 | 最新一次 **basic70 通过**（交付分 85.6，约 1 小时、35 次模型调用）；80 分完整规范仍未通过（柱廊细节与植被分布为部分实现）。前两次因 S13 未交付，约 47 次调用 |

已知限制：

1. **S13 仍是最后的阻断**。修正模型有时找不到合法改法：冻结的灰模种子不允许削切或移动，只能撤回追加细节。此前这种情况会以 `REPAIR_PREVIEW_REQUIRED：未找到成功预览的候选编号` 报错并记为 `failed`；现在会记为“没有合法改法，保留此前最佳候选”（`REPAIR_NO_LEGAL_CHANGE`），任务以最好一轮的 `needs_review` 结束。S13 本身仍需要放宽冻结约束之外的新机制才能修掉。
2. **主体标记偏多**。规划常把几乎所有实例都标为 subject，占幅检查因此很容易通过，资产的主次也被稀释。目前不影响运行，后续会单独修正。
3. **模型波动**。同一输入多次运行，轮次和分数会不同；单次成功不等于稳定。
4. 体素只支持静态、不透明、纯色；格子各轴最多 192，占用最多 50 万格，颜色最多 64 种。照片级场景请用普通模式。

## 9. 自己验证时建议这样做

1. 用一张结构清楚、主体明确的体素图片（自己的作品或有授权的图），生成方式选“按验收目标生成”。
2. 生成中打开“查看执行过程”，确认灰模各轮的阻断项在减少，而不是同一个阻断反复出现。
3. 结束后对照第 5 节检查：
   - 灰模 `gate.json` 的 `passed` 是否为 `true`；
   - 资产是否全部通过；
   - 最终 rawScore 与未通过原因；
   - 三维场景能否打开、`.vox` 能否在 MagicaVoxel 打开。
4. 记录任务 ID、最终状态和调用数。重复 2–3 次同一输入，看结果是否一致。

遇到问题时，请保留任务目录和页面上的错误原文，不要删除记录后重跑。
