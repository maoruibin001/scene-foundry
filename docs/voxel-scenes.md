# 体素场景运行说明

体素模式与普通场景并存。浏览器打开工作台后，点击侧栏“体素场景”，或访问 `http://127.0.0.1:19774/voxel/`。上传同一个场景的 1–5 张体素图片，选择本机 Codex 模型和生成方式，点击“开始生成体素场景”。不需要再人工确认图片：程序记录图片摘要和描述，将它们自动冻结为本次生成与验收的共同目标。这个记录标记为 `uploaded-image-goal`，不会伪称用户做过额外确认。

## 准备与启动

先按 [从零运行手册](run-from-zero.md) 安装固定版本的 Engine、Scene Generator、Python 图像环境和固定材质目录。默认模型提供方式仍为本机普通 `codex`；自定义启动器必须显式配置。体素与普通模式共用已有构建、运行采集、原图对照和独立评分环节。单进程启动仍使用原来的命令：

```sh
cd workbench
PORT=19774 PIPELINE_PROVIDER=codex-cli PIPELINE_CODEX_BIN=codex bun src/server.ts
```

模型和思考深度由页面选择并保存到任务。`PIPELINE_MODEL` 可调整推荐模型，`PIPELINE_MAX_CALLS` 控制累计调用数；预算包含技术重试、格式纠正和独立验收。基础 70 分、80 分等既有标准继续由服务配置决定，体素模式不会替场景加分或放宽运行检查。

如果普通场景 worker 正在进行冻结实验，可以使用新的独立数据目录启动体素 worker，然后只更新界面代理：

```sh
# 独立目录同样需要 Python 环境和固定材质目录；不能借用别的 worker 的任务账本。
PIPELINE_DATA_DIR=/absolute/path/to/voxel-data PORT=19874 \
  PIPELINE_PROVIDER=codex-cli PIPELINE_CODEX_BIN=codex bun src/server.ts

# 原场景后端不变；网页入口仍为 19774。
UI_PORT=19774 UI_UPSTREAM=http://127.0.0.1:19873 \
  VOXEL_UPSTREAM=http://127.0.0.1:19874 bun src/ui-server.ts
```

`/api/voxel/`、`/voxel/files/` 和 `/voxel/process/` 会转发到体素后端。普通 `/api/` 路由仍去原后端。两个 worker 的任务、队列、模型预算和运行目录分开；体素记录在体素入口查看。端口数值只是部署例子，启动前须确认没有被占用。

冻结的体素 worker 执行中需要更新只读过程面板时，可为界面进程设置 `VOXEL_OBSERVER_DATA_DIR=/absolute/path/to/voxel-data`。界面直接读取这个目录的已保存状态与实时输出，支持诊断续跑的第0轮及后续修复目录；写操作保持拒绝。普通API、生成任务、模型请求及 worker 源码不受影响，不能因此把新界面版本当作新的生成验证。

## 管线与产物

1. 使用普通3D相同的模型选择、阶段推理策略和原图验收目标。页面默认采用复杂场景推荐配置，不单独切换低成本模型或固定为medium。
2. 复用普通管线的逐图观察、地标绑定、空间与机位规划、真实Engine灰模验收。空间不合格时先修正，不用后续细节掩盖布局错误。 本地Codex的空间工具先保存核心布局，再分别保存开口与连接声明，完整后才交接；观察阶段冻结的关系由程序按真实地标绑定展开，不让模型重复抄写或改动原要求。
3. 复用共享材质规划和逐资产生成/实际预览；保存每项有效几何和来源，支持既有检查点恢复。体素分支使用共享纯色材质表，避免把参考图的阴影再次烘焙进表面；普通3D的贴图提取流程保留。体素灰模和详细资产可使用原生 `voxelVolume`，用整数格的填充、挖空和重复构造门洞、板条及台阶；交接时固定已接受体积的格距、原点、范围、操作与姿态，允许换材质或增加细节。Codex资产工具按部件保存并校验当前资产，失败修改保留上一个有效检查点，全部部件完成及实际预览通过后才交接。
4. 程序将经过上述检查的几何转为 `voxel-grid-v2`。可共格的原生体积直接映射实际占用格，不重新采样表面；支持整数细分的轴缩放及90度旋转。不满足共同格精度或固定范围、任意角度旋转、实际贴图材料均显式回退旧采样并标记精度尚未证实。其他几何仍使用三角形/格子交叠和封闭体绕数检查；其真实交叠可能占据另一体积的空隙。所有实例保持身份、需求绑定和世界机位；任一实体完全丢失即拒绝。CPU转换在独立进程执行，网页和实时日志继续响应。
5. 对体素化后的场景执行同一个Engine构建、运行采集、原图对照和独立评分。自动修正使用保存的制作源和实际体素画面；修正工具的Engine预览同样先体素化。基础70门槛、原始诊断分、关键缺失、规范和运行硬检查均保留，不给体素额外加分。
6. 保存 `voxel-source-scene.json`（冻结制作源）、`voxelization-report.json`（离散化范围、实体占用和颜色证据）、`voxel-program.json`（可回放占用格）、`voxel-metrics.json`、可编辑 `scene.vox`、运行工程、截图、录屏和评审证据。最佳候选的制作源、体素数据、产物和评分一起恢复，下载包包含这些对应证据。

新的体素任务执行完整共享流程，调用预留也与普通3D一致。`按验收目标生成`沿用持续质量修正与连续无有效改善停止策略；累计模型预算仍约束所有初稿、纠正、技术恢复和评审。另可选有限修正或仅首轮。自动验收通过表示该次输入达标；只有既有固定批次发布门槛全部通过才可发布稳定版本，单次成功或下载成功不能替代稳定性认证。旧 `voxel-scene-v1` 记录保留原始数据，并支持显式重建；新生成不再让模型一次输出整场景体素操作。

空间执行超时而已有合法核心布局时，最多保留一次范围线框的本地渲染，明确标记尚未生成完整几何或体素、尚未验收。此诊断草稿不计入还原成功率；取消、外部预算/认证故障或资源不足不会触发额外渲染。原错误、实际调用、质量修正和写入次数继续保留。

体素详情页展示原图、Engine 画面、颜色表和所有实体的过程入口，支持打开真实三维预览、下载 `.vox` 和运行包。执行过程里的模型输出是只读订阅，关闭页面不会中断生成。

正交参考机位的构图测量、可见性深度和校准射线使用平行投影及真实覆盖高度；切换机位时保留各自画幅。局部空间修正可显式调整正交覆盖高度，不能通过无效的FOV变化假装改变正交占幅。Engine 回执读取实际 Camera 组件的投影类型、视场、正交范围与裁剪面，当前预览契约不接受只有声明而没有实际投影证据的回执。旧来源缺少投影回执时，最多对同一几何和机位作一次零模型调用的实际诊断重放，不改写旧运行记录或重新评分。历史诊断保持原测量版本，不能把测量算法更正当成图像质量提升。

体素局部修正可使用有界网格拟合工具：最多3个实例、2个轴，每次修正共24次预测，拟合不能改动冻结的图片目标、地标身份或观测依据。只有确实测得的投影误差进入计算；预测结果必须重新经过真实Engine预览与独立评审，不能用预测报告直接放行。

按质量边界停止的灰模任务可在详情页查看实际画面和各轮评分。冻结的新版本经过机制验证后，“按诊断修正空间”入口沿用选定的原灰模、需求、参考图和评审协议继续局部修正。有限历史账本须明确追加最多1至2次修复，累计模型调用上限、原始结果与已用次数都保留；同一冻结版本不能重复申请，外部认证或预算故障不能通过此入口绕过。新任务仍自动提取图片目标，不增加人工确认步骤。

首段局部空间制作超时后，如果保存了唯一合法实拍候选，详情页可通过“继续已保存空间候选”核验检查点并进入独立评分。恢复保留原超时、模型未完成状态、历史调用与修复次数；损坏摘要、目标或编译源码变化、多个实拍候选、其他修正轮、用户取消及外部认证/额度故障均不自动选择。这项执行恢复不表示灰模或成品验收通过。

## 边界

离散格子让结构和颜色更容易约束，也更容易编辑与审计。但一张图片不能确定被遮挡的背面，模型仍可能误判比例、空间关系和机位；`.vox` 合法不代表图片还原通过。当前只支持静态、不透明、纯色体素，格子各轴最多 192、总范围最多 200 万格、占用最多 50 万格、颜色最多 64 种；新共享转换默认请求128格长边，实际分辨率由范围上限确定并明确记录，最多3200万次光栅/填充检查，导出仍受全场景 25 万三角形预算。照片级场景继续使用普通模式。

验证参考图来自真实作品作者 [Thibault Simar / Voxelmade](https://voxelmade.com/gallery/)，例如 [Aztec temple](https://www.voxelmade.com/portfolio-item/aztec-temple/) 和 [Lost Temple](https://www.voxelmade.com/portfolio-item/lost-temple/)。作者作品只用于本地输入验证；仓库不重新分发图片。导出格式依据 [MagicaVoxel 官方 VOX 格式](https://github.com/ephtracy/voxel-model/blob/master/MagicaVoxel-file-format-vox.txt)。网页支持和格式验证、真实运行通过、图片还原达标是三个独立的验证结果。

## 2026-10-08 验证结果

这次从正常网页入口上传两张真实作品，使用普通本地 `codex`、`gpt-6-luna / medium`。实际 CLI 回执的模型、深度和供应商均与选择一致；16 次累计调用包含初次失败、格式纠正和视觉修正，不把续跑作为新的预算。

| 输入 | 体素与真实运行 | 独立图片验收 |
| --- | --- | --- |
| Aztec temple | 40,686 个占用格；可运行、可编辑导出；11 项运行硬检查通过 | 三轮 7.9 / 8.3 / 5.2 分，均未达到基础 70 分。按既有候选选择规则保留第 0 轮 7.9 分；没有把更晚轮次或可运行状态标记为验收通过。 |
| Lost Temple | 37,627 个占用格；端口隔离修复后，11 项运行硬检查通过 | 渲染完成时累计 16 次调用已用尽，因此独立评分未执行，状态为受阻，不能宣称还原达标。 |

两个案例均从页面实际下载 `.vox` 和运行证据包；独立核对占用格、颜色索引、包内文件摘要和渲染产物摘要，下载的体素与选中候选一致。1019 项工作台测试与 3 项模板检查通过。真实渲染、机位控制和下载链路证明基础能力可运行；目前尚未证明自动图片还原能力达标，尤其仍存在原图机位、遮挡和形态理解问题。该模式保持实验验证状态。

后续零模型调用诊断定位了 Aztec temple 的一个确定缺陷：背景山体先占据了主体上部的范围，主体使用保留已有格的组合策略，导致 9 项上部构造完全没有生成，底座仍在却让实体级检查通过。只改变观察机位的独立 Engine 采集仍显示主体缺失，说明这一问题不能靠换相机解决。

校验现已拒绝被异色、非地面实体完全挡住的主体填充部件，并返回主体、操作序号、格数与遮挡实体，供既有格式纠正环节处理；同色拼接、地面接触和同实体合并仍然允许。提示词也明确：底座存在不能代替上部构造，嵌入地形的主体需要明确替换交叠格或预留正确空间。这项检查只解决已知的完整部件丢失，不评定图像相似度，也不能保证局部遮挡、比例和机位正确。回放保存的 Aztec 输出时，新检查拒绝了被背景山体挡住的主体第 3 项构造；Lost Temple 输出也暴露出水池格全部被石质平台占据的问题，过去的运行通过没有检查出这类视觉内容丢失。两个历史案例保留原始数据和结论，不被改写为修复成功。新增修复的 37 项定向测试通过，修复后的模型生成和独立评分尚未重跑；本次累计 16 次模型调用预算已用尽。
